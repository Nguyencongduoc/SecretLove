## Audio transport decision

Vercel documents a 4.5 MB Function request-body ceiling, but explicitly recommends streamed responses when response bodies exceed that ceiling. A Web ReadableStream is therefore the delivery candidate; upload remains a distinct blocker. See [Vercel body-size guidance](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions) and [streaming functions](https://vercel.com/docs/functions/streaming-functions). This is platform guidance, not an executed deployment test.

Delivery design: keep existing same-origin owner/recipient endpoints and DAL authorization before Storage access. Fetch only the authorized server-generated object path from private Supabase Storage using server credentials, forward a normalized single Range upstream, validate status/size/range/MIME before returning bytes, and stream with backpressure/cancellation/deadline/concurrency bounds. Never redirect, expose credentials/object paths, or mint public/signed download URLs. Responses are private/no-store; full/range stream bodies are never accumulated into an SDK Blob or arrayBuffer. HEAD/invalid-range metadata follows authorization. A stream authorized at its start can deliver in-flight bytes after revocation; later requests recheck access. Already delivered audio cannot be recalled. Session expiry/unpublish/delete/Close retain existing checks and client teardown. No claim of instant cancellation of every in-flight stream.

Uploads cannot be fixed by streaming the **response** or increasing Next's buffer. Keep the approved 16 MiB/360-second product cap. The user selected A; B/C are evaluated alternatives, not implemented:

| Option | Concrete plan | Security/operations trade-offs |
| --- | --- | --- |
| A — same-origin chunks (recommended for existing privacy boundary) | Creator begins a draft/version/owner-authorized ingest; sends indexed <=1 MiB chunks through authenticated/Origin-checked routes to private staging; server verifies manifest and assembles <=16 MiB, decodes/strips tags with existing inspector, uploads sanitized final object, then transactionally finalizes attachment | No browser Storage grants or bearer Storage URL. More requests/DB state and transient raw bytes. Requires reviewed additive 008, one active ingest/letter, creator byte/backlog/part quotas, expiry, version locks, idempotent parts/finalization and durable staging cleanup. Publication blocked while ingest pending. No asset ready before inspection. |
| B — signed upload to quarantine | Server issues one path-bound no-upsert Supabase upload capability after owner/draft/quota checks; browser uploads to a separate private quarantine bucket; completion triggers server inspection/normalization before existing finalization | Smaller application transfer burden. Supabase documents a two-hour upload-token lifetime; a late upload can outlive cancellation unless cleanup accounts for token expiry. Original unvalidated bytes must never be served. Requires reviewed 008, quota reservation, retry/recreation cleanup, failure handling and explicit approval of this capability/lifetime. No signed **download** URL. |
| C — dedicated Node upload service/hosting | Run the existing bounded validation/upload pipeline behind a separately approved HTTPS same-origin gateway or move the whole application to compatible Node hosting | Preserves inspection before final Storage but introduces another deployment/trust/IP/Origin/session boundary or changes Vercel hosting. Requires provider/budget/operations approval and actual gateway tests. |

Acceptance for A: missing/foreign/revoked ingests deny parts/commit; duplicate parts cannot alter a sealed manifest; total bytes/count bound at 16 MiB; one slot and pending quota reserved before transfer; mutation/upload limits consumed once per ingest plus a separate bounded part budget; publish blocked; tag stripping and codec validation remain server-side; stale/expired/concurrent commit cannot resurrect a detached/deleted/published asset; all staging paths are server-generated and cleanup survives failure. After commit, existing saved-music wire shape and renderer/player are unchanged. Do not claim these proposed controls implemented until the selected design is coded/tested and its migration manually applied.

Implemented A details: `POST /api/letters/{id}/music/ingests` (small strict JSON), `PUT .../{ingestId}/parts/{index}` (binary <=1 MiB), `POST .../{ingestId}` (small commit JSON) and `DELETE .../{ingestId}` (cancel). Owner/Origin checks apply to every entry point. Whole-file and immutable-part SHA-256 manifests are verified; a hash is integrity checking, not licensing/security assurance. One ingest/letter, at most sixteen parts, 15-minute expiry, 90-second commit lease; 120 part requests/min/creator, original mutation/upload budgets unchanged. Existing 60 MiB/100-job budget reserves raw+candidate at 2x declared bytes; staging/queued bytes count. Server assembler <=2/process and 45-second transfer budget plus existing bounded codec decode; sanitized bytes only become ready after current lease/draft/version checks. Parent versions advance at begin and finish/cancel. Client reconciles only the expected version and offers cancel after reload; it never silently adopts concurrent edits. Failed commits keep candidate/staging privately reserved for retry/cancel/expiry. Cleanup v3 handles the third bucket and protects mixed old workers. See CHUNK_AUDIO_SETUP.md.

Download stream slots are held until EOF/cancel/error (max four/process), with a 45-second deadline and upstream redirects/encoding/length/MIME/range mismatches denied. Headers are authorized before response start, GET uses no buffered Content-Length, HEAD remains metadata-only. Supabase sees only the requested canonical range, reducing seek egress. Auth is at request start; slow in-flight bytes can continue until cancellation/deadline, and browser-delivered bytes cannot be recalled. The legacy buffered multipart upload API remains for compatibility/local use; Studio uses chunks. Do not certify that legacy >4.5 MB upload endpoint on Vercel.

Each delivered byte still crosses Supabase-to-Function and Function-to-browser boundaries; budget both providers' egress and Function duration, especially looping/repeated seeks. Chunk staging also requires a server read during commit and a write of sanitized output. Streaming bounds delivery buffering, but commit intentionally assembles a <=16 MiB file for validation and may hold chunk/concatenation/output/decoder buffers concurrently. Per-process concurrency caps are not a fleet-wide cost ceiling: measure target memory/cold-start/load and configure external budgets/alerts before expanding access. A slow download may hit the 45-second deadline; the existing player must report/retry without breaking authorized reading. No provider cost or throughput guarantee is inferred from local passes.

[Supabase signed upload documentation](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl) supports option B's lifetime. Short-lived signed **downloads** are not selected: they would weaken per-request revocation while the token remains valid. Local large-byte streaming tests cannot certify Vercel edge buffering; the approved-target test gate below is mandatory.
